# 开发与项目管理规范（RuleShift / EvoNex）

本文档定义本项目从拆解到交付的约定，作为团队协作与评审的统一依据。

## 1. 工作分解（WBS）

- 以 [RuleShift 计划](ruleshift-development-plan.md) 为当前基准；EvoNex M1–M6 保留为历史记录。
- 新任务使用 GOV-/DATA-/NLP-/SYS-/EVAL-/RELEASE- 编号；本周 GOV-01～04 每项验收后提交推送。
- 子任务编号：`M<模块>-T<任务>`，例如 `T1.2`。实现时可在提交信息中标注，例如
  `feat(data): T1.2 合成数据生成器`。
- 每个任务必须有：目标、关键步骤、交付物、验收标准、负责人/角色。

## 2. 分支与提交约定

### 2.1 分支

- `main`：可运行、可演示的稳定主线。
- 功能分支：`feat/<模块>/<简短描述>`，例如 `feat/m1-data-generator`。
- 修复分支：`fix/<模块>/<简短描述>`。

### 2.2 提交信息

采用 Conventional Commits 中文摘要：

```text
feat(data): 新增 T1.2 合成数据生成器
fix(ontology): 修正种子三元组标准条款引用
docs(plan): 更新里程碑状态
test(eval): 补充 Golden 评测集校验
```

### 2.3 仓库级约定（必须遵守）

每次提交并推送 GitHub 远端 `origin` 前，按根目录 `AGENTS.md`：

1. 检查并总结变更（`git diff` / `git add -A` 后 `git diff --cached`）；
2. 在 `docs/git-diffs/<YYYY-MM-DD>-<简短描述>.md` 保存变更总结（日期、涉及文件、变更要点、注意事项/影响）；
3. 变更与总结一并暂存、提交；
4. 推送远端。

## 3. 代码规范

- Python 3.12+；核心逻辑尽量标准库优先，减少环境依赖。
- 函数/模块提供 docstring；配置、常量集中在文件头部或独立模块。
- JSON/JSONL/CSV 均使用 UTF-8；CSV 输出可用 `utf-8-sig` 便于 Excel。
- 所有合成数据必须可复现：生成器使用固定随机种子与显式参数。
- 禁止把 API Key、Token、真实企业数据提交入库。

## 4. 测试与完成定义（DoD）

- 单测使用标准库 `unittest`，命令：`python -m unittest discover -s tests -v`。
- 数据相关任务必须通过 Schema/一致性测试。
- 智能体相关任务必须能在 Golden 集上给出可复现的指标。
- DoD：代码合入 main 前通过全部测试；演示所需命令写入 README；文档更新到位。

## 5. 文档要求

- 新任务先更新方案/规格，再写代码。
- 涉及“能做什么”的功能描述必须与 Nexent 官方文档一致，不夸大。
- 公开标准及其摘要、翻译和问答须核验对应用途权限；改写不自动免除权利限制。
  数据准入以 [数据治理](data-governance.md) 为准，旧合成演示不等于可用研究语料。

## 6. 协作与评审

- 建议按方案中的角色分工：数据组、图谱组、平台组、评测组、运维交付组。
- 关键变更（Schema、Golden 集、本体版本）由 2 人评审后合入。

## 7. 创新提案与联动更新

- 开发中发现可提升创新性、前沿性、可行性或应用价值的新点子时，先按
  [`docs/innovation-process.md`](innovation-process.md) 形成提案并汇报。
- 小范围、低风险且属于当前授权范围的改进，可在汇报后进入当前迭代；涉及项目目标、
  数据来源/许可、核心架构、模型路线、外部服务、显著成本或排期变化时，须经用户确认后纳入。
- 获准纳入的提案分配 `INNO-YYYY-NNN` 编号，并在
  [`docs/innovation-log.md`](innovation-log.md) 中维护状态、影响范围、验收结果和关联任务。
- 创新任务应拆入现有 WBS，明确依赖关系、负责人、交付物和验收标准；不得以“探索”为由
  绕过数据合规、测试、评测和文档要求。
- 合入前执行联动检查：计划/里程碑、代码、Schema/数据、本体、MCP/API、Agent/Skill、测试、
  评测、部署和演示材料中凡受影响者均已同步；不适用项应在提案或台账中说明原因。

## 8. 简洁工程与文档

- 代码保持单一职责、短函数和明确命名；不为假设需求增加抽象、依赖或重复封装。
- 注释只写原因、边界和外部约束；不复述代码，不记录过程，不用注释替代重构。公共接口保留简短 docstring。
- DOCX 仅在确需办公文档时生成；使用 `documents` 技能创建或编辑，并渲染为 PNG 逐页检查布局、字体、表格和截断。
- Markdown、JSON 或代码足够表达时不额外生成 DOCX；文档保持单一事实源，通过链接引用详细规则。
