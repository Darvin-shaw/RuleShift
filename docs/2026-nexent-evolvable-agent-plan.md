# 「衡策 EvoNex」— 基于 Nexent 的可进化制造质量决策智能体

> 2026-09-07：本文保留为历史方案。当前开发以 [RuleShift 计划](ruleshift-development-plan.md)
> 与仓库 README 为准。以下能力、指标和排期包括原始设想，不代表 RuleShift 的实现进度。

> 一句话：面向**先进制造**场景，用「资产认知 + 本体共建 + 检索-推理双引擎 + 反馈进化」四层架构，把企业沉睡的 PDF 规程、Excel 台账、质检图片等异构存量数据，变成**有 ID、有图谱、可检索、可推理、可追溯、可进化**的决策资产，全部落地在 Nexent 平台上，并沉淀为可复用的 Skill 模板。

## 0. 赛题拆解：四句话对应四件事

| 赛题要求 | 我们如何承接 | 对应的 Nexent 原生能力/自建部分 |
|---|---|---|

**得分主张**：多数参赛队会做成「一个 Nexent 知识库 + 一个问答智能体」的 RAG Demo；我们把它升级为「**能说明数据从哪来、知识怎么长、结论怎么推、错了怎么改**」的完整可演示系统，并让每一步都能在 Nexent 界面上看到证据与执行过程。

## 1. 创意与差异化：把“可进化”做成真实闭环

项目取名为 **衡策（EvoNex）**，寓意“每一条决策都经权衡、有依据”。

五个演进闭环构成产品主线：

1. **汇（感知）**：新文件进库 → 多模态解析 → 生成资产卡片 → 入资产台账。
2. **铸（知识）**：资产卡片/问答上下文 → 本体候选三元组 → 置信度分级 → 人工点确认/驳回 → 图谱写入。
3. **衡（决策）**：问题 → 检索（向量+关键词+图谱+表格）→ 分步推理 → 反证检索 → 形成证据链。
4. **溯（透明）**：每条结论挂引用与出处，全链路 Mermaid 呈现，可一键导出报告。
5. **进（演化）**：用户反馈 + 离线评测 → 触发版本迭代 → 回归对比 → 通过才发布/回滚。

亮点可以这样向评委讲：

- **不是一次性 RAG**：智能体每轮问答的“答错/答对/缺引用”都会回流，驱动本体、检索策略和提示词的下一版本。
- **真多模态**：不只解析 PDF，还演示“表格台账 → 数值证据”“缺陷图片/控制图 → 视觉证据”如何进入同一条决策链。
- **真低资源**：标注只需要少量种子规则与人工确认，不做大规模标注。
- **真可溯源**：结论 = 事实 + 依据条款 + 推理步 + 反证检查，而不是一段不可解释的生成文本。
- **Deep Nexent-native**：知识库、Skills、MCP、A2A、北向 API、版本管理全部用上，而不是把 Nexent 当聊天壳。

## 2. 场景与数据集设计（先进制造，建议主打“工艺质量合规决策”）

### 2.1 为什么选先进制造

- 数据天然是“多模态异构”：工艺规程/标准是 PDF 文本，检验记录/SPC 台账是 Excel/CSV，缺陷照片与控制图是图片——赛题四个硬性要求能一次集齐。
- 决策链足够复杂且可客观评价：缺陷是否放行、返工/报废/让步接收，必须引用具体条款与检测证据，适合“多跳推理 + 溯源”。
- 低资源场景真实：企业很少有成规模标注好的质量知识图谱，正好体现我们的半自动构建价值。

### 2.2 虚构企业资产样本（全部可离线生成）

以一家虚构精密制造企业“**衡星精工**”为 Demo 主体，产品为电机轴、齿轮箱。

| 类型 | 内容 | 数量建议（P0） | 来源方式 |
|---|---|---|---|
| 规程/标准文本 | 企业工艺规程、检验规范、不合格品控制程序、质量手册；公开标准片段（如 GB/T 19001 相关条款改写摘要，标注出处） | 15–25 份 PDF/Markdown | 自编 + 公开标准条款改写（注意不整篇转载） |
| 表格类 | SPC 过程能力台账、来料/成品检验记录、不合格品台账、设备维保记录、客诉台账 | 30–60 个 CSV/XLSX | 脚本生成（含可复现随机种子） |
| 图片类 | 缺陷照片/表面检测图、控制图截图、检验报告扫描件、标签与证书图 | 40–80 张 | 脚本生成控制图/截图；缺陷图可引用公开数据集或自绘变体 |
| 关联主数据 | 产品 BOM、工序路线、设备清单、人员/班次表 | 5–10 个文件 | 脚本生成 |

为了可分享，所有企业资料均为**虚构合成数据**；公开发表的标准只放“条款标题+要点”式的二次整理并注明来源，不整篇复制，避免开源许可问题。

### 2.3 两类核心 Demo 问题（P0 必须跑通）

1. **多跳根因类**：问“2025 年 5 月 A 型电机轴硬度不合格是否与 3 号热处理炉温漂相关？依据是什么？”要求智能体串起：检验台账 → SPC 控制图 → 维保记录 → 工艺规程/标准条款 → 设备故障记录，输出证据链。
2. **处置决策类**：问“该批次 42 件不合格品能否让步接收？”要求智能体查《不合格品控制程序》与客户合同条款、算风险范围，给出“返工/报废/让步接收 + 条件 + 审批路径”并逐条引用出处。

P1 可加一条“标准更新冲击”演示：导入 2026 版检验标准后，智能体自动提示本体与条款的差异，并重新评估一个此前通过的批次。

## 3. 总体架构

```mermaid
flowchart TB
    U[用户: 提问/上传附件] --> M[主智能体: 衡策·质量决策<br/>Nexent 发布版]
    M --> R1[规划模式与任务拆解]
    M --> R2[多智能体/并行工具调用]

    R2 --> KB[(Nexent 知识库<br/>规程库/台账库/图片库)]
    R2 --> KG[(自建图谱 Neo4j<br/>通过 kg_ontology_server MCP)]
    R2 --> AS[资产认知 MCP<br/>多模态解析+资产卡片]
    R2 --> FT[官方 Skill 与自建 Skill]

    KG --> ONTO[本体共建: 候选抽取→置信度→人工确认]
    ONTO --> ST[标准对齐与漂移报告]
    M --> EV[自检/证据审计]
    EV --> ANS[证据链答案<br/>引用[[S1]] + 来源面板 + Mermaid]
    ANS --> FB[用户反馈日志]
    FB --> EVA[离线评测/回归]
    EVA --> VER[Nexent 版本管理: 发布或回滚]
```

### 3.1 分层说明

**L1 数据与资产认知层**

- 主用 Nexent 官方能力：上传 PDF/Word/Excel/图片 → 解析 → 向量化（文本用 text embedding，图片库用 multi-embedding）。
- 自建 `asset_cognition_server`（MCP）补足“资产标识”：
  - `parse_upload_to_asset_card`：将解析结果规范成资产卡片 JSON；
  - `register_asset`：写入资产台账（Asset ID、来源文件、模态、文档类型、业务标签、解析状态、质量分）；
  - `find_assets_by_entity`：按“批次号/产品号/设备号/检测项”反向找相关资产。
- 资产卡片示例：

```json
{
  "asset_id": "AST-20250607-0031",
  "source_file": "spc_axis_a_may.xlsx",
  "modality": "table",
  "doc_type": "spc_trace",
  "business_tags": ["A型电机轴", "硬度", "2025-05"],
  "entities": ["衡星精工", "电机轴A", "3号热处理炉"],
  "chunk_ids": ["chunk_1120"],
  "checksum": "sha256:...",
  "ingested_at": "2026-09-01T10:00:00Z"
}
```

**L2 本体共建层（低资源半自动）**

种子本体 v1（约 12 类、15 关系），完全由方案文档定义：

- 类：产品/零件、批次、工序、设备、测量项、检验记录、缺陷类型、标准文件、标准条款、处置决策、角色、风险等级。
- 关系示例：`批次-经工序-生产`、`设备-执行工序`、`检验记录-检出-缺陷`、`缺陷-判定依据-标准条款`、`决策-允许-处置动作`、`处置-影响-批次范围`。
- 每个三元组带 `confidence`、`source_chunk`、`review_status`、`ontology_version`。

低资源构建策略：

1. **种子引导**：从标准条款/检验规则表格中做模式抽取（如“允许/不允许/返工/报废/让步”规则表），把几十条规则程序化转成种子三元组，不依赖大语料标注。
2. **LLM 候选抽取**：用少量示例提示，把规程、台账、问答文本转成候选三元组与候选实体；
3. **置信度分级**：模式命中/多文档一致/LLM 自信 分高；单源低置信归为“待确认”；
4. **人工确认闭环**：在 Nexent 对话中由“图谱运营官”智能体生成核对清单，用户逐条“确认/驳回/修正”；也支持导出 CSV 批量审核；
5. **标准对齐与漂移检测**：维护“本体概念 ↔ 标准条款 ID”映射；新标准入库后自动比对，输出差异与影响资产列表；
6. **版本化**：每次本体变更写入事件日志，可导出 v1/v2 diff。

**L3 检索-推理双驱动执行流**

- 检索侧（Evidence Retriever）：
  - 向量/关键词混合检索（官方 `search-knowledge-base`/`knowledge_base_search`）；
  - 图谱检索（MCP：实体上下文、n 跳邻居、批次-工序-设备关系）；
  - 表格/数值检索（先定位台账，再按列语义过滤行）；
  - 需要实时信息时可加官方公网搜索 Skill。
- 推理侧（Reasoning Engine）：
  - 规划模式把复杂问题拆成 3–8 步；
  - ReAct 循环中每一步“先取证据、再下论断、再检查反证”；
  - 自检节点覆盖：检索结果是否空、证据是否够、工具是否出错、最终答案是否遗漏引用；
  - 输出统一“决策证据链 JSON”并渲染成 Mermaid + 引用标记。

> 双驱动不是两个独立 Agent，而是同一执行流里的两条“车道”：检索负责把候选事实压缩到最小证据集，推理负责判断哪些证据真正支持结论、哪些只是相关。主智能体可通过 A2A 或子智能体并行跑“证据收集”和“反证搜索”。

**L4 进化闭环与模板层**

- 每个会话写入反馈日志：正确答案/推荐证据/用户纠错/漏引用；
- 每周（或按触发）跑离线评测集（20–40 条 golden QA）得到指标矩阵；
- 自动生成“新版本草稿”：本体候选增量、Skill 提示优化建议、检索参数调整、知识库摘要刷新；
- 用 Nexent 智能体版本管理做 A/B 对比：新版本指标不下降才发布，否则回滚——这是“可进化且可控”的最好证据。
- 把验证过的工作流沉淀为 Skill 模板，并附一个“跨行业迁移演示”（见 5.4）。

## 4. 与 Nexent 的集成清单（写进交付物，避免“只用了聊天界面”）

### 4.1 自建 MCP 服务

| MCP Server | 主要工具 | 用途 |
|---|---|---|
| `asset_cognition_server`（Python，FastMCP） | `parse_upload_to_asset_card`、`register_asset`、`find_assets_by_entity`、`table_column_infer` | 多模态资产卡片化 |

接入方式按官方文档：远程 URL / 容器化 MCP / OpenAPI 转 MCP 均可；P0 用容器化或本地远程，保证评委环境可复现。

### 4.2 自建 Skill（放进 `skills/` 并以 ZIP 上传 Nexent Skill 仓库）

|---|---|---|
| `asset-cognition` | Tool Skill | 新文件入库时统一走“解析→卡片→注册” |

| `standard-alignment` | Agent Skill | 新标准导入时对齐本体并生成漂移报告 |
| `evidence-decision` | Agent Skill | 所有质量决策类问题的标准工作流 |
| `quality-report-docx` | Tool Skill | 基于官方 `create-docx` 生成可下载决策报告 |

### 4.3 智能体编排

| 智能体 | 英文变量名 | 角色 |

## 5. 子任务清单（建议按 6 周拆解，每项均标负责人）

> 分工角色：**数据组**（场景数据/资产卡片/金标测试集）、**图谱组**（本体 Schema/抽取/Neo4j）、**平台组**（Nexent 部署/MCP/Skill/智能体编排）、**评测组**（评测集/指标/反馈闭环）、**运维交付组**（部署文档/开源仓库/演示）。

### M1 场景与数据工程（第 1–2 周）

#### T1.1 场景与数据规格说明书

- **目标**：把 2.2/2.3 落地为可生成的数据规格。
- **内容**：确定产品/工序/设备/缺陷的实体清单；设计文件命名与引用关系；画 2–3 条 golden 决策链。
- **交付物**：`docs/data-spec.md` + 实体-文件映射表。
- **验收**：数据规格能让不同组员独立生成的数据在批次号上互相连通。
- **负责人**：数据组。

#### T1.2 合成数据生成器

- **目标**：一键复现全部 Demo 数据（可离线）。
- **内容**：编写 `scripts/generate_synthetic_data.py`，产出规程 PDF、检验/SPC/维保/客诉台账 CSV/XLSX、控制图与缺陷图片。
- **交付物**：`data/generated/*` + 生成脚本 + 随机种子说明。
- **验收**：全新环境执行一条命令即可生成完整语料，10 分钟内完成。
- **负责人**：数据组 + 平台组。

#### T1.3 多模态解析与资产卡片管线

- **目标**：验证 Nexent 内置解析 + 自建 MCP 组合能产出统一资产卡片。
- **内容**：先跑通官方 `analyze_text_file`/`analyze_image`；再实现 `asset_cognition_server` 的解析、表头推断、图片 OCR/图型识别（VLM）、资产注册。
- **交付物**：可调用的 MCP 工具 + `assets_ledger.csv/jsonl` + 资产卡片 schema。
- **验收**：随机抽查 20 个资产卡片，关键字段（类型、批次、模态、来源）准确率 ≥90%。
- **负责人**：数据组（主）+ 平台组。

#### T1.4 Golden 评测集 v1

- **目标**：先立评测标尺，防止后期“自说自话”。
- **内容**：编写 20 条 QA（10 条多跳根因、5 条处置决策、5 条表格数值/图片识别），每条标注：标准答案 + 必备证据链（必须引用哪些文件/条款）+ 干扰证据（不应引用哪些）。
- **交付物**：`tests/golden/*.json`。
- **验收**：2 位成员独立可复现标注，证据链标注一致率 ≥90%。
- **负责人**：评测组（主）+ 数据组。

### M2 平台环境与基础集成（第 1–3 周，可与 M1 并行）

#### T2.1 Nexent 部署与模型接入

- **目标**：本地 Docker Compose 起 Nexent，完成模型/知识库配置。
- **内容**：按官方 Docker 部署（建议 8 核 16GB/100GB 磁盘；最低 4 核 8GB）；接入 OpenAI 兼容 LLM（如 Qwen/DeepSeek/SiliconFlow）、视觉 VLM、文本 Embedding；若图片入库则配 multi-embedding。
- **交付物**：`deploy/` 启动文档 + `.env.example` + 部署截图。
- **验收**：管理员可建知识库、智能体，聊天可回答带引用的基础问题。
- **负责人**：运维交付组。

#### T2.2 知识库体系建立

- **目标**：把语料按用途分区，并验证检索质量。
- **内容**：建 3 个知识库：`标准规程库`（PDF/MD）、`台账与记录库`（Excel/CSV）、`图片证据库`（图片+解析文本）；配置 chunk 策略、自摘要周期；对关键表格提前做“表格转文本摘要”预处理以提升命中率。
- **交付物**：知识库清单 + 导入脚本 + 检索效果抽样报告。
- **验收**：10 条代表性查询，Hit@5 ≥ 0.8。
- **负责人**：平台组（主）+ 数据组。

#### T2.3 MCP 服务脚手架与安全

- **目标**：三个 MCP Server 能注册进 Nexent 并可“工具测试”。
- **内容**：FastMCP 项目脚手架、容器化或远程配置、工具参数 Schema、鉴权；先接 Neo4j（或轻量 SQLite 图替代，避免评委环境太重）。
- **交付物**：`mcp_servers/` 可运行代码 + 配置样例 + 测试报告。
- **验收**：每个工具在 Nexent「测试工具」面板返回预期 JSON。
- **负责人**：平台组。

### M3 本体与低资源构建（第 3–4 周）

#### T3.1 本体 Schema v1 与种子知识

- **目标**：确定可执行的类/关系/属性/标准映射模板。
- **内容**：写 Schema 文档 + YAML/JSON 定义；从检验规则表做程序化种子抽取（30–60 条真值三元组）。
- **交付物**：`ontology/schema-v1.*` + `ontology/seed-triples.jsonl`。
- **验收**：种子三元组全部有来源条款、可被 SQL/Cypher 查询。
- **负责人**：图谱组。

#### T3.2 候选抽取管线

- **目标**：LLM + 规则双通道产出候选三元组。
- **内容**：设计少样本抽取提示；对规程/台账/资产卡片文本批量抽取；实现文档共指/消歧（统一“3号炉”“三号热处理炉”）；输出 `candidate-triples.jsonl`（含 confidence、来源、状态）。
- **交付物**：抽取脚本 + 候选集 + 抽取质量报告。
- **验收**：候选三元组 precision ≥ 0.6（人工抽查），其中高置信批次 ≥ 0.75。
- **负责人**：图谱组（主）+ 数据组。

#### T3.3 人工确认闭环（Skill + 界面）

- **目标**：让审核工作通过 Nexent 对话完成，而不是脱离平台。
- **内容**：开发 `ontology-co-builder` Skill：输入待审清单 → 生成逐条卡片 → 用户“确认/驳回/修正” → 写回图谱并记录 `reviewed_by`；支持批量 CSV 审核。
- **交付物**：Skill 包 + 审核演示视频片段。
- **验收**：10 分钟内完成一轮 50 条候选审核；驳回原因可统计。
- **负责人**：图谱组（主）+ 平台组。

#### T3.4 标准对齐与增量更新

- **目标**：证明本体“能随新标准/新文档动态更新”。
- **内容**：实现 `standard_align`（本体概念↔条款 ID 映射）与 `ontology_diff`（变更影响面）；做一次“旧版标准 → 2026 版”更新演示。
- **交付物**：对齐映射文件 + 漂移报告样例 + 更新后版本 diff。
- **验收**：标准变更后 1 分钟内输出影响到的工序/条款/资产清单。
- **负责人**：图谱组。

### M4 检索-推理协同执行流（第 4–5 周）

#### T4.1 检索路由与查询分解

- **目标**：让智能体知道“这个问题该查图谱、台账还是图片”。
- **内容**：在 `evidence-decision` Skill 中定义查询路由提示与参数规范；实现查询分解为多个子检索（支持多工具并行）；对台账检索增加“先 schema 后行过滤”的提示约束。
- **交付物**：路由规则文档 + 至少 5 条典型查询的执行样例。
- **验收**：20 条 golden 上，正确工具选择率 ≥85%。
- **负责人**：平台组（主）+ 评测组。

#### T4.2 证据链决策流程

- **目标**：把两条 golden 决策链完整跑通。
- **内容**：编写 `evidence-decision` Skill 的步骤化指令：拆题 → 找事实 → 找条款 → 推结论 → 查反证 → 标引用；输出决策证据链 JSON（每条论断含 evidence_id、来源、置信度、是否为反证）。
- **交付物**：Skill + 证据链 JSON schema + 两条完整 Demo 录屏。
- **验收**：回答可做到“每条结论都带引用；引用缺失时主动说明证据不足”。
- **负责人**：平台组（主）+ 图谱组/评测组。

#### T4.3 智能体编排与自检

- **目标**：主智能体稳定调用子智能体/工具并启用自检。
- **内容**：配置 `quality_decision` 主智能体 + 子智能体；打开规划模式、自检、运行摘要；测试多工具并行与 A2A 调用；调大/调小最大步数做压力实验。
- **交付物**：agent 导出 JSON/ZIP（可导入复现）+ 编排关系截图。
- **验收**：同一问题连续跑 3 次，不出现无引用断言或死循环。
- **负责人**：平台组。

#### T4.4 溯源展示与报告生成

- **目标**：把“证据链”变成评委看得懂的成果物。
- **内容**：答案中使用官方引用 `[[S1]]` + 来源面板；用 Mermaid 画决策流程图（Nexent 原生渲染）；封装 `quality-report-docx` 生成带证据附件的报告。
- **交付物**：1 份完整样例报告（Markdown/DOCX）+ 来源面板截图。
- **验收**：报告可由第三方按证据链反查原文，无断链。
- **负责人**：数据组（主）+ 平台组。

### M5 进化闭环与模板沉淀（第 5–6 周）

#### T5.1 反馈与离线评测 Harness

- **目标**：量化“新版本更好还是更差”。
- **内容**：跑 20–40 条 golden，输出指标：答案正确率、证据召回/精确、溯源完整度（每条断言是否带引用）、工具选择准确率、多跳深度；把用户纠错/漏引用落成可回放样本。
- **交付物**：`tests/run_eval.py` + 指标看板（Markdown/CSV）。
- **验收**：任一修改后一条命令可跑完全量评测并在 30 分钟内出报告。
- **负责人**：评测组。

#### T5.2 演化演示（版本 A/B 与回滚）

- **目标**：向评委演示“智能体如何越用越好且可控”。
- **内容**：注入 2026 版标准 + 若干反馈样本 → 生成新版本草稿（本体增量 + Skill 提示更新）→ 离线回归 → 达标发布/不达标回滚；用 Nexent 版本对比截图展示。
- **交付物**：演化演示脚本 + 前后版本指标对比表 + 录屏。
- **验收**：演示中明确出现“新标准导致 v2 修正了 2 条决策、回归无退化”的证据。
- **负责人**：评测组（主）+ 图谱组/平台组。

#### T5.3 Skill 模板沉淀与跨行业迁移样例

- **目标**：证明“资产认知/本体共建/证据决策”工作流可复用。
- **内容**：把 5 个 Skill 参数化、写模板说明（输入语料 → 输出资产卡片/本体/证据链）；P1 做一个轻量迁移样例（如把“质量决策”模板套到政务政策匹配或金融尽调问答，仅 3–5 条示例问题即可，不铺开）。
- **交付物**：`skills/templates/` + 迁移指南 + 迁移样例报告。
- **验收**：模板文档能让另一组在 2 天内搭出新场景雏形。
- **负责人**：数据组 + 平台组。

#### T5.4 开源仓库整理

- **目标**：满足“作品开源至 GitCode/GitHub”。
- **内容**：整理目录、README（含部署/数据生成/评测/演示四步）、License 与第三方数据版权声明、隐私说明（全部合成数据）；把 Nexent 智能体配置导出 ZIP 作为一键导入资产。
- **交付物**：完整公开仓库。
- **验收**：全新机器按 README 可复现：部署 → 导数据 → 导入智能体 → 跑通 2 条 Demo。
- **负责人**：运维交付组（主）+ 全体。

### M6 验收与路演（第 6 周末）

#### T6.1 赛题对照自评表

## 8. 关键风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 本地资源不足，Nexent 跑不动 | 阻塞开发 | 按 8C/16G 规划；尽量复用一个实例；Neo4j 可用 SQLite 图降级 |
| 无海外模型/API 或断网 | Demo 中断 | 优先国内 OpenAI 兼容模型；准备离线合成数据与录屏兜底 |
| 图片/表格检索不准 | 多模态亮点变弱点 | 表格预转结构化摘要；图片用 VLM 解析后把“图像事实文本化”入向量库 |
| LLM 幻觉导致错误决策 | 答辩被质疑 | 全程引用 + 自检 + 反证步骤 + 证据链 JSON；演示问题固定为黄金用例 |
| 本体构建被评委认为“不是真知识图谱” | 减分 | 图谱可查询/可 diff/可随标准更新，评审时直接跑 Cypher 查询演示 |
| 开源合规（标准文本/图片版权） | 作品违规 | 只用自编合成数据与公开数据的二次改写；附 THIRD_PARTY_NOTICES |

## 9. 一句话总结

衡策 EvoNex 把赛题从“做一个会问答的智能体”重新定义为“**让一套行业知识系统在小样本下长出来、在检索与推理中把话说清、在反馈中持续进化**”，并保证它不是一个 PPT 概念，而是一套在 Nexent 上能演示、能评测、能回滚、能开源的工程系统。
